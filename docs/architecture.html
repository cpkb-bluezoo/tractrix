Architecture

How bytes become events — and how the writer sits beside the parser.

Parse pipeline

Parser
  ├── ExternalEntityDecoder   bytes → chars (BOM, XML/text decl, charset, EOL)
  └── Scanner                 chars → XmlHandler events (WF, DTD, validation)
        └── optional NamespaceFilter   xmlns attrs → namespace() events
ComponentRole
Parser Owns decoder + scanner. Public entry: receive, close, reset, parse_all.
ExternalEntityDecoder Detects BOM and declarations, decodes via encoding_rs (UTF-32 manually), normalises line endings.
Scanner Hot-path well-formedness + optional DTD validation. Namespace-unaware.
NamespaceFilter Optional stage in front of your app handler; emits namespace and rewrites qNames.
XmlHandler Your code. Push callbacks — no token stream, no DOM.

No document tree

Tractrix does not build an AST. The serializable surface of a parse is the XmlHandler event vocabulary. Applications that need a tree materialise one themselves from those events.

Writer

XmlWriter is a sibling API, not an XmlHandler implementor. It is an imperative streaming serializer (write_start_element, …) with options matching Gonzalez XMLWriter. You can bridge parse → write in your own handler (see Parse → write).

Ownership and lifetimes

  • The handler is borrowed for the lifetime of Parser (&mut dyn XmlHandler).
  • FeatureSet is consulted at construction; keep it stable while parsing (some features refuse mid-parse changes).
  • Optional EntityResolver is boxed into the scanner for external DTD/entity loads.
  • XmlWriter owns its Write sink; close/flush do not close the sink.

Non-goals

  • SAX/JAXP ContentHandler compatibility layer
  • XSLT / XPath / XQuery
  • XML Schema / RELAX NG (DTD only)
  • Built-in DOM
  • Async runtime integration (feed Bytes from your own I/O)
